# KnifeAngle: BLE-датчик угла заточки на HOLYIOT-21011

Датчик крепится на нож и по BLE передаёт угол наклона относительно положения
«нож плашмя на камне». Целевой угол и индикация «в цели» живут на веб-странице
(Web Bluetooth). Прошивка только измеряет и передаёт угол.

| Этап | Что | Статус |
|---|---|---|
| 0 | Диагностическая прошивка: проверка акселерометра, кварца, кнопки, LED, System OFF | **готово, ждёт проверки на железе** |
| 1 | Основная прошивка (угол, калибровка, кнопка, BLE GATT) | после этапа 0 |
| 2 | Проверка в nRF Connect | после этапа 1 |
| 3 | Веб-страница `web/index.html` | после этапа 2 |
| 4 | Расчёт тока и автономности на CR2032 | после этапа 3 |

## Железо

Схемы именно 21011 нет. Пины взяты со схемы **HOLYIOT-21014 V1.0** (2021/11/13).
Это та же плата, но с RGB-светодиодом. Совпадение разводки для 21011 v1.0
подтверждается двумя независимыми источниками:
- [DevZone #119888](https://devzone.nordicsemi.com/f/nordic-q-a/119888/i2c-functions-don-t-work-but-using-the-i2c-shell-does):
  на «HolyIOT-21011-v1.0» LIS2DH12 отвечал (WHO_AM_I = 0x33) на P0.02/P0.05 с питанием от P0.08;
- [MiloshCZ/holyiot-21014-bthome-button](https://github.com/MiloshCZ/holyiot-21014-bthome-button):
  у 21011 v1.0 кнопка на P0.31 (активный высокий), светодиод на P0.30 (активный низкий).

| Сигнал | Пин nRF52810 | Примечание |
|---|---|---|
| LIS2DH12 SCK / SCL | P0.05 | |
| LIS2DH12 SDI / SDA (MOSI) | P0.02 | |
| LIS2DH12 SDO / SA0 (MISO) | P0.03 | |
| LIS2DH12 CS | P0.04 | 0 = SPI, 1 = I2C |
| LIS2DH12 INT1 / INT2 | P0.06 / P0.07 | |
| **LVCC: питание LIS2DH12** | **P0.08** | датчик питается от GPIO, в ВЫКЛ питание полностью снимается |
| Кнопка KEY | P0.31 | на VDD, подтяжка 100 кОм к GND: нажата = 1 |
| Светодиод (красный) | P0.30 | анод на VDD, катод через 1 кОм: горит при 0 |
| Кварц 32.768 кГц | P0.00 / P0.01 | на схеме есть, наличие на 21011 проверяет этап 0 |
| Кварц 32 МГц | XC1 / XC2 | обязателен для радио, есть |
| SWD | площадки T1..T4 | VDD, GND, SWDIO, SWDCLK |

Акселерометр по схеме подключён по **SPI**, а не по I2C, как предполагалось. Чип
поддерживает оба интерфейса на тех же ножках. Диагностика проверяет оба, основная
прошивка будет работать по SPI.

## Тулчейн: почему upstream Zephyr, а не nRF Connect SDK

Используется **Zephyr v4.4.2** и **Zephyr SDK 1.0.1** (GCC 14).
- Zephyr и есть ОС, на которой построен nRF Connect SDK. Код приложения тот же.
- В upstream Zephyr есть свой открытый BLE-контроллер (`BT_LL_SW_SPLIT`). Он
  собирается в тот же образ, поэтому **SoftDevice не нужен**: один `.hex`/`.bin` с адреса 0.
- Для сборки нужны Zephyr и всего 4 модуля (≈1 ГБ исходников без истории). У NCS
  десятки репозиториев. Так сборка проще и воспроизводимее.
- Платы Holyiot (21014) уже есть в upstream, поэтому описание 21011 сделано по их образцу.

Под NCS проект, скорее всего, тоже соберётся (там будет SoftDevice Controller, тоже в том
же образе), но я это не проверял.

## Сборка

Нужен Linux или macOS (на Windows через WSL2), Python ≥ 3.10, CMake ≥ 3.20, Ninja, Git.

```bash
# 1. Воркспейс и west
mkdir ~/knife-ws && cd ~/knife-ws
python3 -m venv .venv && . .venv/bin/activate
pip install west

git clone https://github.com/Antehich/knife_sharpening.git
west init -l knife_sharpening
west update --narrow -o=--depth=1          # zephyr + cmsis_6, hal_nordic, mbedtls, tf-psa-crypto
pip install -r zephyr/scripts/requirements-base.txt
west zephyr-export

# 2. Zephyr SDK 1.0.1 (только ARM-тулчейн)
wget https://github.com/zephyrproject-rtos/sdk-ng/releases/download/v1.0.1/zephyr-sdk-1.0.1_linux-x86_64_minimal.tar.xz
tar xf zephyr-sdk-1.0.1_linux-x86_64_minimal.tar.xz
./zephyr-sdk-1.0.1/setup.sh -t arm-zephyr-eabi -c

# 3. Сборка (образы появятся в knife_sharpening/prebuilt/<app>/)
./knife_sharpening/scripts/build.sh diag
# то же вручную:
west build -p -b holyiot_21011 knife_sharpening/firmware/diag
#   -> build/zephyr/zephyr.hex и build/zephyr/zephyr.bin
```

Образ начинается с адреса `0x00000000` (загрузчика нет) и ничего не пишет в UICR.
Поэтому `.bin` полностью равен содержимому `.hex`, и его можно заливать со смещением 0.

Готовые образы лежат в `prebuilt/`, собирать самому не обязательно.

## Заливка через ESP32_nRF52_SWD (atc1441)

### Подключение

| nRF52 (площадки на плате) | ESP32-S3 |
|---|---|
| SWDCLK (T4) | GPIO, указанный в `platformio.ini` флэшера как SWDCLK (по умолчанию 21) |
| SWDIO (T3) | GPIO SWDIO (по умолчанию 19) |
| GND (T2) | GND |
| VDD (T1) | 3.3 V, **только если батарейка вынута** |

> ⚠️ Нельзя одновременно подавать 3.3 В на VDD и держать CR2032 в держателе: внешние
> 3.3 В пойдут в литиевую батарейку (её нельзя заряжать). Либо батарейка, либо 3.3 В
> от ESP32, но не вместе.

### Шаги в веб-интерфейсе флэшера

1. Откройте `http://<IP ESP32>/` и нажмите **Init SWD**. В блоке «nRF info» должно
   появиться `Connected`, а размер flash должен быть 192 kB.
2. Нажмите **Erase nRF**. Это полное стирание через CTRL-AP (ERASEALL): оно снимает
   APPROTECT и **навсегда удаляет заводскую прошивку Holyiot**, а также калибровку.
3. Снова нажмите **Init SWD**: чип теперь должен быть «unlocked».
4. В блоке **Flash Uploaded File** укажите `Offset 0x` = `0`, выберите
   `prebuilt/diag/knife_diag.bin` и нажмите **Flash Uploaded File**. Флэшер сам flash
   не стирает, поэтому шаг 2 обязателен.
5. Проверка (по желанию): **Download Flash** с `Offset 0`, `Size` = размер `.bin` в hex
   (для диагностики `E7BC`). Сравните с исходным файлом.
6. Нажмите **Reset nRF** или передёрните питание.

**Повторная прошивка:** всегда начинайте с **Erase nRF**. На новых ревизиях nRF52810
(hardened APPROTECT) после каждого сброса доступ по SWD снова закрывается, потому что
UICR.APPROTECT не записан (в `.bin` UICR не попадает). ERASEALL работает всегда, глитчер
не нужен.

## Этап 0: диагностическая прошивка

`prebuilt/diag/knife_diag.bin` (≈58 КБ). Ничего не перебирает вслепую: работает только с
пинами по схеме.

### Что делает

1. Сразу после старта проверяет кварц 32.768 кГц: запускает его, ждёт до 2 с и меряет
   частоту по RTC0 (нужно ≈3277 тиков за 100 мс). Потом останавливает его, а BLE
   работает от внутреннего RC-генератора. Если кварца нет, первая вспышка будет через ~2 с.
2. **1 вспышка**: прошивка запустилась.
3. Включает питание датчика (P0.08) и читает WHO_AM_I по SPI. Если ответа нет, пробует
   I2C на тех же ножках, адреса 0x19 и 0x18. Результат вспышками:
   **2 вспышки**: акселерометр найден; **5 быстрых**: не найден.
4. Запускает акселерометр (25 Гц, ±2 g, высокое разрешение) и начинает BLE-рекламу
   (интервал 500 мс). Каждые 200 мс обновляет ускорения, угол, кнопку и напряжение.
5. **Удержание кнопки ≥1.5 с**: длинная вспышка 0.6 с, питание датчика снимается,
   чип уходит в System OFF. **Следующее нажатие** будит его (в диагностике будит любое
   нажатие). Через 30 минут прошивка уходит в System OFF сама.

Если светодиод горит постоянно и гаснет только на «вспышках», значит полярность
обратная. Сообщите мне.

### Что смотреть в nRF Connect (Android/iOS)

Вкладка **Scanner**, найдите устройство с именем вида **`KAD S33 X1 B0`**:

| Часть имени | Значение |
|---|---|
| `S` / `I` / `i` / `N` | акселерометр найден по SPI / по I2C 0x19 / по I2C 0x18 / не найден |
| `33` | WHO_AM_I в hex (ожидается `33`; при `N` здесь последнее прочитанное по SPI значение) |
| `X1` / `X0` | кварц 32.768 кГц работает / нет |
| `B0` / `B1` | кнопка отпущена / нажата (обновляется раз в 0.5 с) |

Устройство не подключаемое. Подробности в **manufacturer data** (Company ID `0xFFFF`),
это видно, если раскрыть строку устройства. Байты после Company ID:

| Байт | Поле | Ожидается |
|---|---|---|
| 0 | версия диагностики | `01` |
| 1 | шина: `00` нет, `01` SPI, `02` I2C 0x19, `03` I2C 0x18 | `01` |
| 2 | WHO_AM_I по SPI | `33` |
| 3 | WHO_AM_I по I2C (`00`, если I2C не проверялся) | `00` |
| 4 | кварц 32 кГц: `01` работает, `00` нет | ? |
| 5–6 | тиков кварца за 100 мс, uint16 LE | ≈`CD 0C` (3277) |
| 7 | флаги: bit0 кнопка нажата, bit1 проснулся из System OFF, bit2 сброс пином, bit3 программный сброс, bit4 watchdog, bit5 lockup | |
| 8–9 | X, mg, int16 LE | |
| 10–11 | Y, mg, int16 LE | |
| 12–13 | Z, mg, int16 LE | плата горизонтально: ≈`E8 03` (+1000) или `18 FC` (−1000) |
| 14–15 | угол между осью Z и вертикалью, 0.1°, uint16 LE | плашмя: около 0 или 1800 |
| 16–17 | напряжение VDD, мВ, uint16 LE | CR2032: ≈`B8 0B` (3000) |
| 18 | счётчик обновлений | растёт |

### Чек-лист для проверки (пришлите результаты)

1. Сколько вспышек после установки батарейки: 1 + 2 или 1 + 5? Не горит ли светодиод постоянно?
2. Имя в nRF Connect целиком (например, `KAD S33 X1 B0`).
3. Байты manufacturer data (скриншот или текст), плата лежит горизонтально.
4. Меняются ли X/Y/Z и угол, если наклонять плату? При повороте на 90° угол ≈ 900.
5. Становится ли `B1` при нажатии кнопки?
6. Удержание 1.5 с: была длинная вспышка, реклама пропала? Короткое нажатие: устройство
   снова появилось, и в байте 7 стоит bit1 (значение `x2`/`x3`)?
7. Если можете рассмотреть плату: есть ли у вывода DCC (пин 47) дроссель 10 мкГн и
   маленький дроссель 15 нГн. От этого зависит, можно ли включать DC/DC (ток радио
   и процессора примерно на треть меньше).

По результатам основная прошивка (этап 1) получит правильный источник 32 кГц
(кварц или RC), шину и режим питания.

## Допущения

1. **Разводка 21011 v1.0 совпадает со схемой 21014 V1.0** по акселерометру
   (P0.02–P0.08), кнопке (P0.31) и кварцам. Светодиод на 21011 один, P0.30, активный
   низкий. Этап 0 это проверяет.
2. **Чип nRF52810-QFAA** (так в задании). В обсуждении на DevZone у такой же платы указан
   nRF52832 (корпуса совместимы по выводам). Образ для 52810 должен работать и на 52832,
   но если у вас 52832, скажите: поменяю SoC в описании платы.
3. **Акселерометр LIS2DH12** (по схеме). По WHO_AM_I (0x33) его не отличить от LIS3DH, но
   регистры, нужные прошивке, у них совпадают.
4. **Источник 32 кГц: внутренний RC** (работает при любой комплектации). Кварц будет
   включён, если этап 0 покажет `X1`.
5. **DC/DC выключен** (работает LDO), пока не подтверждено наличие дросселей. Включается
   сборкой с `DCDC=1 ./scripts/build.sh ...` (`boards/dcdc.overlay`).
6. **Без загрузчика:** образ с адреса 0, UICR не используется (вывод nRESET не
   переназначается), поэтому `.bin` = `.hex`. Последние 8 КБ flash (0x2E000–0x2FFFF)
   отведены под хранение калибровки (этап 1).
7. **APPROTECT** прошивкой не трогается (поведение Zephyr по умолчанию). На новых ревизиях
   чипа поэтому перед каждой перепрошивкой нужен Erase nRF. При этом стирается и калибровка.
8. **Мощность передатчика 0 дБм** (по умолчанию). Её можно снизить до −4…−8 дБм для
   экономии, если дальность не важна (решим на этапе 4).
9. Заводская прошивка Holyiot при первой заливке стирается без возможности восстановления.
